# QA道場 — 仕様から、品質を見抜く。

QAエンジニア向けの**実践型テストトレーニング**。問題の選択肢を答えるのではなく、仕様を読み、自分でテストを設計し、意図的に不具合が組み込まれた模擬アプリを実際に操作して、不具合報告まで行います。

## 公開先

https://k-yumoto-ist.github.io/qa-dojo/

> 初回はリポジトリの **Settings → Pages → Build and deployment → Source → GitHub Actions** を選択してください。これが設定されていない場合、ワークフローのデプロイが失敗することがあります。

## 実装済みの演習


ホーム画面は**アプリの画面イメージから選べるギャラリー**です。5種類のアプリをカード・左右ボタン・横スクロールで選択し、テスト設計／探索的テストを切り替えて開始できます。選択中のアプリ・モードはURLに反映され、各カードには現在のモードで保存した進捗を表示します。開始済みの演習ではボタンが「修行を再開する」に変わります。

修行の流れはアイコン付きで表示し、探索モードでは設計ステップを除いた3段階に切り替わります。説明や詳細スコアは折りたたみ、スマホではカードを横にスワイプできます。プレビュー画像は画面イメージで、実際の演習の仕様は修行内の仕様書を参照してください。

**修行の答え合わせ**

不具合報告を1件以上登録すると、報告ステップで「答え合わせを開く」を使えるようになります。5つの意図的不具合について、仕様ID・再現手順・期待結果・実際の結果を確認でき、発見済み・未観測・報告受理も区別します。受理済み報告には、その不具合の具体的な解説を即時表示します。

判定は従来通り**該当観点の不具合が操作で観測されたかどうか**のみを確認します。記述した再現手順や期待結果・実際の結果の正確さを自動評価するものではありません。答え合わせの開放状態はアプリ・モードごとにローカル保存されます。

**2つの修行モード**

- テスト設計型：仕様 → テスト設計 → 実機操作 → 不具合報告（設計30点、操作40点、報告30点）
- 探索的テスト：仕様 → すぐに実機操作 → 不具合報告（操作50点、報告50点）。操作中の気づきは任意の「探索メモ」に保存できます。メモは採点対象外です。

探索型は `?mode=explore` のURLで切り替えられ、データは `qa-dojo:explore:v1` に独立保存されます。既存の設計型の `qa-dojo:training:v1` データは保持されます。


**Level 01: ECサイトの注文フォーム**

1. **仕様理解:** 注文数量、送料、クーポン、メールアドレス、備考の期待仕様を確認。
2. **テスト設計:** 観点・前提・手順・期待結果を自分で記述して保存。
3. **実機検証:** 実際の注文フォームに入力し、計算結果や注文処理を確認。操作ログが残ります。
4. **不具合報告:** 観点、再現手順、期待結果、実際の結果を記載。事前に該当する挙動を観測している場合にルールベースで受理します。

採点は、登録したテスト観点（最大30点）、観測した意図的不具合（最大40点）、有効な不具合報告（最大30点）に基づく**定型ルール**です。文章の意味理解・AI評価はありません。実務的なテスト設計／報告の品質については、指導者によるレビューを想定しています。

## 選べるアプリケーション

ダッシュボードから以下の5種類を選べます。すべてテスト設計型・探索的テストの両方に対応し、各アプリの仕様書・観点・模擬画面・操作ログ・報告照合を用意しています。

| アプリ | 主な練習内容 |
| --- | --- |
| ECサイトの注文フォーム | 数量・送料・クーポン・入力チェック |
| 会議室予約 | 日時・利用人数・重複・キャンセル後の再予約 |
| 会員登録 | パスワード・確認入力・年齢・規約同意・重複メール |
| 商品検索・絞り込み | 価格帯・複合条件・在庫・並び順 |
| 経費申請・承認 | 税額・領収書・操作権限・承認後の更新と取り下げ |

URLの `app=booking` / `signup` / `search` / `expense` で直接選択できます。例えば `?app=booking&mode=explore` は予約アプリの探索的テストです。省略時や未知のIDではEC注文に戻ります。

記録はアプリとモードの組み合わせごとに独立保存します。既存のEC演習の保存キーは変更していません。リセットとJSON書き出しは選択中のアプリ・モードだけが対象です。追加アプリの「模擬データを初期化」では、テストケース・操作ログ・観測・報告を残したまま入力と登録データだけを戻せます。

予約日は演習用の2026年11月に固定しています。会員登録の入力欄のパスワード・確認入力は保存・操作ログ出力・JSON出力の対象外です。演習には架空の個人情報を使ってください。

## 技術構成

- HTML / CSS / Vanilla JavaScript（フレームワーク・ビルド不要）
- GitHub Pages（`main`へのpushでGitHub Actionsから自動デプロイ）
- ブラウザの localStorage に学習記録を保存
- AI・データベース・サーバー・ログイン機能なし

**データは利用中のブラウザ内だけに保存されます。** 別端末と同期しません。リセットすると消去されます。仕様や不具合の判定ルールはクライアント側コードに含まれるため、開発者ツールで答えを調べることもできます。公開演習環境として意図した制約です。

## ローカル起動

`index.html` をブラウザで開くか、HTTPサーバーで配信してください。

```sh
python3 -m http.server 8000
```

`http://localhost:8000` にアクセスします。

## 新たな演習の追加

共通の学習フローとEC注文は `app.js`、追加アプリの仕様・入力定義・意図的不具合・観測判定は `scenarios.js` にあります。各追加アプリは5種類の不具合観点を持ち、既存の100点満点の配点を共用します。`evaluate()` は画面に表示する挙動と不具合観測を返し、共通側が操作ログ・保存・報告照合を行います。今後はメンターによるレビューやテスト設計テンプレートなどを拡張候補としています。

追加アプリの正常系・異常系・意図的不具合・状態遷移は、依存パッケージ不要で検証できます。

```sh
node --check app.js
node --check scenarios.js
node --test tests/*.test.cjs
```

## UI assets and local preview

アプリのプレビューと背景は生成画像をWebPに最適化しています。UIアイコンは Tabler Icons（MIT、`assets/icons/LICENSE`）を同梱し、実行時のCDN依存は追加していません。静的配信・ビルド不要の構成を維持しています。

開発用プレビューは `npm ci` → `npm run dev -- --host 0.0.0.0 --port 4173 --strictPort` でも起動できます。Viteは開発時のみ使用します。

修行画面もホームと共通の配色・フォーム・ステップナビゲーションに統一しています。仕様は項目別に開閉でき、設計・操作・報告中にも「仕様を確認する」から参照できます。観点ボタンは入力中のフォームを再描画せず選択欄へ反映し、ヒントは必要なときだけ開きます。操作ログは最初は閉じ、操作の記録後に開きます。

## UI/UXレビュー（独立演習）

ホームの専用入口、または `ux.html` から、写真付きの架空会議室予約サービス「roomly」を使えます。入社直後の社員が移動中に部屋を確保する利用シナリオを提示し、一覧・検索・詳細・予約・自分の予約・取消を操作します。

操作中に「違和感を記録」から問題・利用者への影響・改善案を記述し、1件以上の指摘を提出すると改善案3問を開放します。選択問題だけをルール採点し、自由記述は自動判定しません。正解例・影響・満たす条件を確認後、改善前／改善後の操作比較ができます。

記録キーは `qa-dojo:ux-review:meeting:v1` で機能テストから独立しています。単一の進行中予約を扱う演習です。日時は2026年11月の固定データ、空室状況は演習用の固定状態で、実在の施設への予約・認証・外部通信はありません。生成写真は各室のイメージです。
